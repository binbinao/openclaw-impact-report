进一步用脚本自身的函数（同 UA、同 URL、同 15 s 超时）连打 2 次：两次均 15.35 s TimeoutError。 随后做 4 臂 × 2 轮对照（script UA / probe UA / 无 UA / curl UA，同 URL 含 start=0）：

轮次script UAprobe UA无 UAcurl UA
第 1 轮Timeout 15.37 s200 / 11.59 s200 / 0.39 s200 / 0.40 s
第 2 轮200 / 0.40 s200 / 0.39 s200 / 0.43 s200 / 0.39 s

结论必须写成「不可归因」：第 1 轮看起来像 UA 封禁（3 失败 vs 0），第 2 轮立刻自我推翻（script UA 0.40 s 成功）。 n=10 且顺序混杂 —— 这正是规则 BJ 说的「单点观测双向无效」：既不能据此定罪 UA，也不能据此为 UA 脱罪。

但有一条可确定的事实：所有失败都发生在 REQUEST_TIMEOUT = 15 的边界上（15.34 / 15.35 / 15.37 s）， 且同一时刻存在 0.38–0.44 s 的成功响应，也存在 11.59 s 的慢响应。失败形态 = 延迟尖峰撞上客户端超时， 而非 HTTP 4xx/5xx。零成本修法仍然只有一条：把异常类型与 HTTP 状态码写进 JSON—— knowledge_ingest.py:47 的 except Exception: return None 把 TimeoutError / 429 / DNS 全部抹平成一句硬编码文案， 这已是第 15 期。

可操作建议 把 REQUEST_TIMEOUT 15 → 30 s 并加 1 次重试

本期实测：同一分钟内有 4 次 0.38–0.44 s 的成功响应。若超时阈值为 30 s + 一次重试， 即使首次落在 15.35 s 的尖峰上，第二次几乎必然成功。这不是「绕过缺陷」，而是让客户端超时匹配观测到的延迟分布 （观测域 0.38 s – >15.35 s）。仍需审批后应用（设计原则 #1）。

失准解剖 三项失准，两个根因，且都不是数据问题

根因 A · 同一事件被拆成两项计分（新规则 BL）。 #3「零 ERROR 第 8 日」与 #6「尾窗 ERROR 仍 0」是同一个事件的两种写法： 一条 ERROR 落盘同时击穿两项。这违背规则 D（预测表逐项自洽）的计分侧 —— 护栏型指标的一张表里，同一序列只能出现一次。若不拆分，本期准确率是 7/9，而不是被扣两次的 7/10。

根因 B · 把预测值当作测量值（规则 BB 的第 2 次实证，这次带完整序列）。 #4 预测 incidents = 77，实测 75。逐日回溯：

09-17 → 3 · 09-18 → 5 · … · 10-20 → 69 · 10-21 → 71 · 10-22 → 73 · 10-23 → 75
（自 09-17 起 每日精确 +2，37 日零例外）

而 P146 记 73（应 71）、P147 记 75（应 73）—— 两次报告都比真值高 2。 基线在本期首次被真正重算，于是恒等式 75 + 2 = 77 的预测必然落空。教训：确定性计数器的基线也必须在当期重新测量， 「+2/日」是恒等式，「起点」不是。

规则 BL · 同一护栏序列在一张预测表里只能计分一次。 若两项预测的取值由同一条记录的存废决定（如「零 ERROR 第 N 日」与「尾窗 ERROR = 0」）， 它们不是两次独立验证，而是一次事件的双重计价 —— 命中时虚高、破裂时虚低。计分前先做事件去重。
规则 BM · 汇总型预测不得把非 live profile 视为零增量。 「合计 = 上期合计 + live 日增量」隐含「其他 profile 本期不产生 ERROR」，而 reviewer 侧每天都有独立的 provider 风险面。本期实测 14,095 vs 预测 14,094，差 1 条正是那个被假设为零的增量。 汇总必须逐 profile 给出增量（规则 BF 的预测侧对应）。
规则 BN · 「超时」与「封禁」在单次观测上不可区分。 本期 arXiv 对照实验中，第 1 轮 script UA 超时 15.37 s、其余三臂 200；第 2 轮同一 UA 0.40 s 成功。 ⇒ 任何「UA / IP / 编码被封」的结论，都必须先排除「客户端超时阈值 < 实际延迟分布」这一更廉价的解释。 判据：失败耗时是否精确等于超时阈值。本期三次失败为 15.34 / 15.35 / 15.37 s（阈值 15 s）—— 全部贴在阈值上 ⇒ 延迟问题，非封禁。规则 BN 是 BJ 的可操作化判据。
