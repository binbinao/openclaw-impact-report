这两分钟里系统没有产生任何作业 —— 那 11 行 100% 是本会话自己的工具调用产生的 （每条 shell 调用写一条 approvals.mode 告警，外加各自的 registry / executor 记录）。 换句话说：「这三条 ERROR 何时出窗」这件事，在本期完全由观察者的调用次数决定。 按 N=44 计，我只要再做 44 次 shell 调用，尾窗 ERROR 就会在本期分析过程中归零 —— 而那不是修复。

③default 是 206 条/日，不是 156 —— 已连错 25 天

上期预测 #7 写「writer 144 / default 156 ⇒ 300 ERROR/日」，判 ✓。但逐日实测： default 自 2026-09-26 起连续 25 天精确 206 条/日 （164 条 weixin + 42 条结构余量，方差为 0）。所以那道 ✓ 是对着旧记忆自证， 系统真实的 live ERROR 是 350 条/日（206 + 144），上期报的 300 少了 17%。

这不是小误差：它同时意味着「weixin 占系统 ERROR 的 96%」这个长期结论一直是低估的分母。 按新口径：weixin 相关 308 / 350 = 88.0%；Session expired 单签名 288 / 350 = 82.3%。

④条件式预测给了二元输出，实测是中间态

上期 #3：「尾窗 ERROR = 0 当且仅当 24h 内新增 ≥ 129 物理行；产出 <129 则仍为 5」。 实际新增 84 行（<129），尾窗 ERROR 是 3。逻辑上「未清空」是对的， 但输出空间只写了 {0, 5} 两个值 —— 而真实轨迹是 5 → 3 → 0，每条证据各有自己的出窗时刻。

正确写法应是「第 k 条证据出窗 ⇔ 新增 ≥ Nk 行」的全序表：N=10/51/52。 门槛式预测把一个序列压成了一个布尔值。

规则 BB

「引用基线」型预测是伪命中 —— 基线会漂移，必须每期实测

当预测写成「X = 上次记录的值」时，命中只证明记忆一致，不证明系统状态。成本极低（一次计数）， 但没有做，就得到了一道 ✓ 和一个错 17% 的结论。

实证：default errors.log 自 2026-09-26 起连续 25 天精确 206 条/日（164 weixin + 42 结构余量，零方差）， 而文档自 P131 起记 156 条/日。P144 #7「writer 144 / default 156 ⇒ 300」判 ✓，实测 350。

操作性：凡涉及长期基线的预测项，须在本期重新计数一次并注明「本期实测」；引用历史常量时必须标注该常量的测定日期，超过 7 日即视为未标定。与规则 AA（阈值代回自检）同族：都是「把记忆当测量」的失效。

规则 BC

观察者可以成为「证据出窗」的唯一驱动力

规则 N / AD / AF 讲的是观察者放大自身的簇；本期证明它还能单方面决定别人的证据何时消失。

实证：09:00:43 快照 N = 10 / 51 / 52；09:02:41 快照 N = 2 / 43 / 44。两分钟内窗口前进 11 行， 这 11 行全部由本会话的工具调用产生（每 shell 调用写一条 approval 告警）。系统侧零作业运行。 换言之：只要再调用 44 次 shell，尾窗 ERROR 就会在本期分析过程中归零 —— 而检测器会把它记为「弱点消失」。

操作性：报告「某证据已出窗 / 弱点归零」时，必须同时给出 (a) 该期证据位次 N，(b) 观察者在本期产生的物理行数。若 N ≤ 观察者行数，则结论不可归因于系统，只能记为「观测预算内出窗」。与规则 L ①（窗口位移）串联：位移的执行者可能就是报告者本人。

规则 BD

条件式预测的输出空间须为全序，不得二元

「若新增 ≥ N 则 0，否则仍为 M」把一条序列压成了一个布尔值。多条证据各有独立位次， 中间态是常态而非例外。

实证：P144 #3 写「否则仍为 5」，实测 3 —— 新增 84 行（<129）时，位次 10 与 51 之外的两条已经出窗。 本期快照进一步把它拆成 N = 2 / 43 / 44 的全序表。

操作性：凡「门槛 ⇒ 状态」的预测，须列出每个状态对应的阈值对（k 条证据出窗 ⇔ 新增 ≥ Nk）， 并声明计数快照时刻（规则 AD′）。允许的输出空间是 {0, 1, …, M}，不是 {0, M}。

规则 BE

冻结档案的 ERROR 不得计入当前错误率

枚举（规则 T 扩展②）解决的是「有没有读」，但没解决「读到的是不是活的」。一个 35 天没写过一个字节的 errors.log 里的 5,450 条 ERROR，与今天的系统健康毫无关系，却和「当前错误率」放在同一张表里。

实证：7 profile 合计 13,194 条 ERROR，其中 analyst 5,450 / researcher 1,144 / orchestrator 464 / developer 22 = 7,080 条（53.7%） 全部来自末记录为 2026-09-15 08:11–08:12 的冻结 profile（同一个已消失的 API_SERVER_KEY 故障）。 活跃口径下 live ERROR = default 206 + writer 144 = 350 条/日；直接相加会得到 38 倍的假分母。

操作性：profile 枚举后必须做第二步——按末记录时间与文件 mtime 判定活跃性，活跃者计入当前错误率，冻结者单列为「档案层」并注明冻结天数。与规则 AM（口径：单项 vs 全 profile）、规则 V（物理行 / 记录 / 事件）共同构成计数的三段前置：枚举 → 判活 → 分单位。
