核心论点：2026 年 AI 训练已进入"万卡时代"——Meta Llama3 在 16384 H100 上训练，字节 MegaScale 在 12288 GPU 上达 55.2% MFU。K8s 默认调度器无法胜任，五大调度平台分工明确：Volcano（批训练首选）、KubeRay（弹性训练/RLHF）、Slurm on K8s（HPC 传统 + LLM 新场景）、Karmada（多集群联邦）、DRA（K8s 1.30+ 下一代 GPU 共享）。2026 年 GPU 利用率从 40% → 70% 是核心 KPI。

行业背景：万卡训练的调度困境

Llama3 故障率启示

Meta 官方披露的数据：
  • Llama3 405B 训练：16384 块 H100 80GB 集群
  • 持续时间：54 天
  • 硬件故障：419 次中断
  • 平均崩溃间隔：每 3 小时崩溃一次
含义："大型训练系统唯一确定的，便是软硬件故障。"——万卡集群需要极强的容错调度、checkpoint 频密化、动态迁移能力。

GPU 利用率瓶颈

2026 年行业基准：
  • 万卡集群 GPU 利用率 行业顶尖水平 60%（很多集群 < 40%）
  • 字节 MegaScale 在 12288 GPU 上达 55.2% MFU（vs Megatron-LM 提升 1.34 倍）
  • 故障 + 通信等待 + 队列碎片化 = 30-50% 算力浪费

Volcano —— AI 训练批调度的事实标准

核心架构

Volcano 架构层次：
  1. K8s 之上：通过 CRD 定义 PodGroup（集体调度单元）、Queue（队列）、Job（VCJob）
  2. 扩展调度器：替换/扩展 kube-scheduler，新增 Plugin（gang / drf / capacity / priority / topology / numa 等）
  3. Controller 链：podgroup-controller、queue-controller、vcjob-controller 协调 Job 生命周期
  4. Webhook：用于 quota admission、PodGroup 注入

核心特性

特性解决的问题实际价值
Gang Scheduling64 卡必须同时就绪，否则部分 Pod 空转训练任务 100% 启动，无碎片化
Queue + Priority多团队共享 GPU 集群，谁优先？支持 priority preemption + fair share
Topology Aware（v1.12+）NVLink/RDMA 跨机柜带宽差，调度到最近TCP 通信带宽 4-10× 提升（字节实测）
DRF（公平份额）资源类型异构（GPU + CPU + 显存）避免大模型任务独占
InfiniBand UFM 自动发现（v1.13）IB 集群拓扑自动构建无需手工建拓扑
多调度器架构（v1.14）训练 + 推理 + Agent 共享集群统一调度平台化

2026 年里程碑（Volcano v1.14）

  • 多调度器架构：不同 workload 用不同调度实例
  • AgentCube：AI Agent 场景专用调度
  • Katana：LLM 推理路由（含 Prefill-Decode disaggregation + KV Cache 感知）
  • 统一 AI 调度平台：训练 + 推理 + Agent 一站式
重要事实：Volcano v1.13（2025-09） 引入完整的网络拓扑感知调度，v1.14（2026-02） 标志其从"批调度器"演化为"AI 时代统一调度平台"。这是当下大厂最流行的 AI 训练调度方案。

KubeRay —— 弹性 AI 训练首选

核心定位

KubeRay = Ray 的 K8s Operator
  • Ray：UC Berkeley RISELab 开源的分布式 Python 框架（已毕业 CNCF）
  • KubeRay：让 Ray 集群跑在 K8s 上的 Operator（由 Anyscale + 社区维护）
  • 核心场景：弹性训练（弹性扩缩容）、RLHF（PPO/DPO）、超参搜索（Ray Tune）、推理服务（Ray Serve）

为什么大模型需要 KubeRay？

AI 训练子场景传统调度痛点KubeRay 解决方式
RLHF/RL 训练PPO 算法中 actor/critic/resource 比例动态变化Ray Actor 弹性扩缩 + autoscaler
混合精度多实验10 个超参实验同时排队Ray Job + Dynamic resource allocation
推理 + 训练混合实时服务占用资源Ray Serve 优先级机制
容错训练节点故障导致整个 Job 重启Ray 内置 actor fault tolerance

缺点与场景

KubeRay 的局限：
  • Gang Scheduling 仍依赖 Volcano 等外部组件——KubeRay 自己不做排队
  • Ray 的 Python GIL 在大规模同步训练时受限，纯数据并行训练不如 Megatron-LM/DeepSpeed 高效
  • 生态绑定 Ray，学习成本高
  • 适用场景：RLHF、多实验、超参搜索、弹性推理。
    不适用：纯大型预训练（如 Llama3 训练）——那种场景用 Volcano + Megatron-Core 更稳

Slurm on K8s —— HPC 传统的回归

为什么 22 年历史的 Slurm 还在用？

关键观察：Slurm 在 HPC 领域已有 22 年历史，但在 LLM 训练时代反而重新走红。
  • 2024-2025 大量 LLM 团队（如 Character.ai、CoreWeave）选择 Slurm 而非纯 K8s
  • 原因：LLM 训练更接近 HPC 工作负载（批处理、长任务、紧耦合通信），Slurm 在这些场景仍是黄金标准

三种部署模式

模式说明代表
SUNK（Slurm on Kubernetes）Slurm 跑 K8s Pod 内，承担调度逻辑CoreWeave、Character.ai
SlonkSlurm + K8s 双调度器协同Character.ai 自研
HybridK8s 启动 Slurm worker 节点，Slurm 调度训练Google Cloud Next 2026 CoreWeave 演示
CoreWeave 在 Google Cloud Next 2026 的方案：
  • 混合调度器：K8s 拉起 GPU 节点（秒级），交给 Slurm 优先级队列
  • Job start latency：从裸金属 Slurm 的"小时级"压到 5 分钟内
  • 对超大规模 + 长任务的 LLM 训练很关键

Slurm vs K8s + Volcano 的选择

混合已成趋势：2026 年的共识是"Slurm + K8s" 二者并存：
  • Slurm 管长训练任务（> 1 小时）
  • K8s 管在线服务 / 短期推理
  • Slurm 调度核心训练，K8s 处理实验性 / 多机多卡小任务

Karmada —— 多集群联邦调度

核心场景

什么时候需要 Karmada？
  • GPU 集群地理分散：北京 + 上海 + 深圳 + 贵阳，分别采购
  • 多云：阿里云 + 腾讯云 + 自建机房
  • 需要统一调度入口，但不希望每个集群独立一套 Volcano

核心技术

特性说明
Kubernetes-native API直接讲 K8s API，对用户透明
调度传播策略ClusterAffinity / SpreadConstraints / Tolerations
多集群应用模板Deployment / Service 自动分发到多集群
与 Volcano 协同CNCF 2025 KubeCon 已展示 Karmada + Volcano 多集群 GPU 调度
2026 现状：Karmada 在分布式 AI 训练场景的生产级落地仍有限（CloudOptimo 2026-05 报告指出）。原因：
  • 跨集群网络带宽受限，万卡分布式训练基本要同集群
  • RDMA/IB 跨集群方案不成熟
  • 主战场仍在跨云/多区推理服务，不在训练

DRA —— K8s 原生下一代 GPU 调度

什么是 DRA

DRA = Dynamic Resource Allocation
  • K8s 1.30 GA（2024-04），1.34 持续完善
  • 核心概念：ResourceClaim（资源申请）+ ResourceSlice（可分配资源）
  • 由 NVIDIA DRA Driver 处理 MIG / MPS 等 GPU 共享场景

三大云厂商落地

云厂商DRA 状态关键能力
AKS（Azure）2026-03 公开博客 + GA 推进MIG + DRA 集成，解决"小模型推理争抢大模型资源"
GKE（Google）Standard 集群 GA，GPU DRA Preview支持 MIG、MPS、time-sharing 互斥
TKE（腾讯云）官方文档覆盖 DRAAgentic AI 应用部署 + 极致资源效能
DRA 的关键价值：改变 K8s GPU 资源的"绑定"语义——传统是 Pod 启动时绑定一整张卡，DRA 允许动态申请 MIG 实例 / MPS 份额 / 时间片。对推理 + 训练混合集群是革命性能力。

三大行业落地案例

案例 1：字节跳动 MegaScale（12288 GPU）

核心数据：
  • 规模：12288 GPU 训练 175B LLM
  • MFU（Model FLOPs Utilization）：55.2%
  • 提升幅度：vs Megatron-LM 1.34 倍
  • 调度策略：TP 组强亲和性（同一 POD / 机柜内部）
调度关键动作：
  1. 亲和性调度：TP 通信最强的 Pod 锁定在同一 POD / 机柜 → 避免 ECMP 哈希冲突
  2. 网络分层：机柜内 NVLink，机柜间 IB + ToR 优化
  3. 应用层优化：融合算子 + 流水线并行调度

案例 2：腾讯云 TKE 的"单集群混合节点"

TKE 的差异化定位（来自腾讯云官方）：
"首创单集群混合节点的资源管理模式，全面围绕 Agentic AI 应用部署与极致资源效能提供全场景解决方案，为用户释放 AI 时代的无限算力。"
  • 单集群混合节点：CPU 节点 + GPU 节点混部，单一 K8s 集群管理
  • Agentic AI 优先：2026 年的差异化卖点
  • DRA + Volcano：训练/推理资源细粒度切分

案例 3：CoreWeave SUNK（Slurm on K8s）

CoreWeave 的混合模式（2026 Google Cloud Next 发布）：
  • K8s 启动 GPU 节点（秒级）
  • Slurm 调度长训练任务（小时-天-周级）
  • Job 启动延迟：从小时级压到 5 分钟
  • 已被多家 LLM 实验室采用为 long-running 训练底座

2026 关键挑战

挑战 1：GPU 利用率

差距：顶尖万卡集群 60% MFU vs 理论 90%+——30% 算力被调度浪费。
解决路径：
  • Volcano 拓扑调度（机柜内 TP 通信）
  • DRA MIG 细粒度切分
  • Slurm + K8s 混合调度（避免队列碎片化）

挑战 2：故障恢复

Llama3 数据：每 3 小时崩溃一次，靠频繁 checkpoint + 动态迁移续命。
调度层关键能力：
  • Volcano Queue 抢占：高优先级任务自动抢占低优先级
  • KubeRay Actor 容错：单节点故障不影响 Job
  • Slurm checkpoint restart：HPC 传统能力

挑战 3：多集群联邦

现实约束：RDMA / IB 跨集群带宽不达标，万卡训练必须同集群。
实际场景：Karmada 多集群调度目前在推理服务（跨云容灾、地理分布）比较成熟，训练场景落地有限。

挑战 4：Agentic AI 新负载

新挑战：Agent 多轮调用 + 工具编排 = 比传统问答 100-1000× Token 消耗。
对调度的影响：
  • 推理 + 训练 + Agent 共享 GPU 集群
  • Volcano v1.14 专门引入 AgentCube 处理
  • DRA 提供细粒度切分基础
