🧬 进化建议

优先级排序（基于影响 × 紧急度 — 本期紧急度全面升级）
conversation_loop 突破 100 条 = 系统级警报。双核心合计 270 条，占总日志 67.3%。连续 8+ 期恶化后，修复方案已不再是建议而是必须。
  • 🔴 1. tool_executor 安全白名单 — 直接消除 41.9% 日志噪声
    168 条/期、⬆ +9.8% 再创新高。10 期累计 +784% (19→168)。连续第 8 期点名。
    方案: 将 ~/.hermes/scripts/ 目录加入安全白名单。或升级安全策略允许已知脚本路径的直接执行。这是唯一能一次消除近半日志噪声的干预。
  • 🔴 2. Provider fallback / secondary_model — 阻止 API 超时风暴
    conversation_loop 102 条，⬆ +15.9% 本期最快速恶化。36 次 APITimeoutError (TokenHub) + 15 次 RateLimitError。
    警告: 如果 TokenHub 完全不可用，整个系统将因模型 API 不可达而瘫痪。
    方案: 配置 secondary_model（如 deepseek-v4-base 或 GPT-4o-mini）+ fallback provider。已在 config.yaml 中预留配置入口——仅需设置 model_fallback 块。
  • 🟡 3. 移除未使用的 Discord 适配器
    连续 12 期点名，51 条/期的无用 ERROR。12.7% 的日志噪声。5 分钟即可在 config.yaml 中移除。
    已错过 12 次修复窗口。唯一不需要代码级修复的弱点——纯配置变更。
  • 🟢 4. InA-Probe active prompting 改进
    本期 arXiv 的 InA-Probe 论文提出主动 instruction-driven probing 替代被动对齐。可在 Hermes 的 skill 选择和 tool 调度中引入主动探测机制——在收到用户指令后先进行意图澄清探测，再匹配最佳工具/skill。这可能同时减少不必要的 terminal 调用（降压 tool_executor）。
  • 🟢 5. 评估 MiMo 1T 模型作为备选 provider
    小米 MiMo-v2.5-Pro-UltraSpeed 以 1000 tok/s 推理速度公开。如果 API 可用且成本合理，1000 tok/s 意味着每次 LLM 调用可控制在亚秒级，从根本上消除 APITimeoutError 的温床。且 1T 参数的模型容量可显著改善 broken_tool_args 等输出质量问题。
