🎯 arXiv：第 5 期连续失败 —— 根因已定位且可一行修复

本轮做了同分钟交替对照实验（同一 UA、同一 IP、立刻相邻的两次请求）：

查询串形态成功失败失败形态
search_query=cat:cs.AI+OR+…（脚本现用，未编码）0/1010/1012.3–15.4 s TimeoutError（7 次）· HTTP 429（3 次）
search_query=cat%3Acs.AI+OR+…（percent-encoded）8/80/8—（HTTP 200 · 0.45–0.75 s · 14,779 B）

结论：决定性变量是 URL 编码，不是 User-Agent（两种 UA 在 encoded 形态下均返回 200）。knowledge_ingest.py 第 64–69 行用 f-string 直接拼接 cat:cs.AI（未编码的冒号），该形态在当前出口链路上被挂起/限流；percent-encoded 形态 100% 成功。

这推翻了 P129–P139 连续 11 期的「瞬时 / 环境」归因 —— 它是一个可复现的代码缺陷。P138 曾记录「重查询成功而脚本仍失败」，本期给出了机制解释；Failed to fetch arXiv API 硬编码文案（第 11 期）使异常类型丢失，掩盖了 429 与 Timeout 的区别。

修复（一行）：

- url = (f"{ARXIV_API}?search_query={cat_string}"
-        f"&sortBy=submittedDate&sortOrder=descending&start=0&max_results={max_results}")
+ import urllib.parse
+ qs = urllib.parse.urlencode({"search_query": " OR ".join(f"cat:{c}" for c in categories),
+                              "sortBy": "submittedDate", "sortOrder": "descending",
+                              "start": 0, "max_results": max_results})
+ url = f"{ARXIV_API}?{qs}"
