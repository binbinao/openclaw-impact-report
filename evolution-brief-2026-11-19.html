头条一 · arXiv 的「全天失败」是一个 3 分钟的窗口

09:01:01 单发失败 → 09:04:07 同一字节串 200 @0.39 s ×3

本期第一次把「源不可用」的宽度测了出来，而不是只测到它的存在。时间线全部为实测：

09:01:01  ✗ knowledge_ingest.py 单发一次  →  Failed to fetch arXiv API（不记录异常类型）
09:02:5x  ✗ 预热 A 序 #1  →  TimeoutError 15.35 s（≈ 阈值 15 s）
09:03:0x  ✗ 预热 A 序 #2  →  TimeoutError 15.61 s
09:03:1x  ✗ 预热 A 序 #3  →  TimeoutError 15.39 s
09:03:3x  ✗ 轻查询（1 分类 / 无 sortBy）→ HTTP 429 @0.71 s
09:03:4x  ✗ 轻查询（同上，逐字节相同）→ HTTP 429 @10.90 s（慢拒）
09:04:0x  ✓ 重查询（3 分类 + sortBy，与预热 A 序逐字节相同）→ 200 @0.39 s · 12,069 B
09:04:0x  ✓ 同上 → 200 @0.39 s · 12,069 B  ·  同上 → 200 @0.40 s · 12,069 B

失败耗时 15.35–15.61 s 全部贴着客户端阈值；成功耗时 0.39 s。比值 39×，而请求字节完全一致。这不是「源坏了」，也不是「阈值太低」——是可用性窗口在 3 分 06 秒内关闭。规则 FD（下立）：单发日采样的「一天不可用」，可能只是一个 3 分钟窗口的一次抽样。

头条二 · 轻查询假说在受限窗口内反转

light（1 分类、无 sortBy）429 · heavy（3 分类 + sortBy）200 —— 成本序反了

DE/DF/DG 曾给出「3 分类 = 31× 成本、轻查询 3/3 成功」的结论。本期在同一分钟窗内重测：轻查询两次全被 429 拒绝（0.71 s 与 10.90 s），而重查询三次全部 200 @0.39 s。规则 FC：查询成本只在源健康窗口内可比；受限窗口内成本序可整体反转（这是规则 ER「按源状态分层」的第二例，第一例是 arXiv 参数顺序）。

头条三 · 两条「余量型」预测同时越界，且都是算术必然

余量 > 阈值 的断言，必须先用「起始余量 − 日耗」代回

P174 预测 default agent.log 余量 ∈ [1.27, 1.36] MB 与 reviewer agent.log 余量 > 3.0 MB，实测 1.23 MB / 2.76 MB，两条同时失准。两者都不是系统行为变化，而是写下时已为假：余量每天固定消耗 ~0.32 / ~0.34 MB，一天后必然低于阈值。规则 FB：报「余量 > X」前必须算 (余量_now − 日耗) ≥ X，否则该预测在生成瞬间即被自己的速率推翻 —— 这是规则 AI（阈值代回）在预算轴上的对偶。
