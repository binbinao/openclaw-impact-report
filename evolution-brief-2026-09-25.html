01🎯 本期头条：同一枚硬币的两面 —— 类别错误可以「漏分」，也可以「错并」

🅐 漏分 —— 解析先于分类：一个 2% 的解析缺口曾等于 100% 的 FUNC 容器

本期生成自然日统计表时，第一次跑出的结果是：agent.tool_executor = 0，连续 11 日。若采信该表，结论将是「本系统 11 天内零功能故障」—— 与 P115 已确证的事实（ddgs 缺陷每日 1–2 次）直接冲突。

根因不是数据、不是容器、也不是分类，而是行格式：agent.tool_executor 的日志行在 level 与 logger 之间多出一个可选字段：

2026-09-25 09:00:18,640 WARNING [cron_9ec6cb79e14d_20260925_090016] agent.tool_executor: Tool web_extract returned error ...
                          ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 仅出现在 cron 会话内的行上
解析器正则未解析行后果
朴素版LEVEL logger: msg150 / 7,666 = 2.0%整个 FUNC 容器归零（executor 0/日）
修正版LEVEL (\[tag\] )?logger: msg4 / 7,692 = 0.05%executor 1–25 条/日，FUNC 明细完整可分解

一个 2% 的解析缺口，恰好等于某一个类别的 100%。这正是 P115「容器 ≠ 类别」警告的下一层：分类之前还有一步解析，而解析器的字段假设同样是隐藏的类别判断。

规则 O（新）· 解析覆盖率自检：任何自建分析脚本在输出任何比例之前，必须先打印 parsed + unparsed == total；未解析率 >0.5% 即判定口径不可用。已知本例是第二次同类事件 —— P113 报「清洁切片 INFRA 100.0% / FUNC 0」很可能同源。

📉 以及一个被高估 2× 的计数

B 通道每天 8 行日志，但真实投递事件只有 2 次/日：

08:01:17,385  gateway.platforms.weixin  send failed            ← 事件 1 第 1 次尝试（live adapter）

规则 P（新）· 日志条数 ≠ 事件数：同一事件被多个 logger 复写时，所有「次/周」「频次」类结论必须除以复写因子。据此，skill 中记录的「微信 rate limit 312+ 次/周」与当前遥测（2 事件/日 = 14 次/周）相差 22× —— 该数字的来源期已不可考，不宜再作为「不用 weixin 交付」的理由。结论（改投递目标）依然成立，但理由应改为：(a) 模型 provider 凭据失效，(b) reviewer 侧平台未配置。

06🧬 进化建议

P0-1 · 把「降低 FUNC」从「消除噪声源种类」改成「修一个作业的 prompt」

实测把真实功能故障的产地压缩到了单点：33/35 = 94.3% 来自 a077650b277d（HN 简报）。其两类主因合计 74.3%：

主因占 FUNC建议动作
web_extract → ddgs 是纯搜索后端，无法抽正文62.9%设置 web.extract_backend；或在作业 prompt 里禁止调用 web_extract，直接用 Python urllib 抓条目页（本简报已用此法，无一条此类错误）
security policy block：& 后台、复合命令命中 hardline 解析上限11.4%作业 prompt 显式禁止 ; && | 复合命令与 & 后台符；改为写脚本文件再执行

预期效果：FUNC 由 3.2 条/日 降至 <0.9 条/日（≈ −72%）。这是本期唯一一条既在本 agent 权限内、又能一次消掉七成真实故障的动作。

P0-2 · 修正 weixin 的因果归属，并把两个作业移出 weixin 投递

  • 真正要修的是 default profile 的 LLM provider 凭据（provider=custom / base_url=http://v2.open.venus.oa…，secretId 报 account parse exception）
  • 若继续把 rate limited 当作根因去调冷却时间，会永远修不好 —— 它只是「作业本已失败、仍尝试投递」的次生现象
  • 规则 R 适用：上述两项均落在 default profile，本 profile 无写权限 → 列为呈报项，不列入 P0 待办

P1 · 检测器与公式改造

  1. weakness_scan.py：增加 WARNING 级别聚合规则（同一签名 ≥10 条 → medium）。已连续 79 期零检出，而尾窗 500/500 行全为 WARNING —— 这是本系统最持久的单一缺陷。
  2. 检测器口径改为时间窗口 + 指数衰减，替代 500 行等容量窗口。本期新增定量证据：同一参数同时造成「FP 存续 2 期（记忆太长）」与「当日 FUNC 不可见（分辨率太低）」，有效延迟已达 4.9 日。
  3. 健康度评分加入信道项：审查后分对 FUNC 的敏感度仅 ≈0.25 分/(条·日⁻¹)，以致在 ddgs 缺陷连续 11 日的情况下仍报 99/100。按 CORDIAL 的思路，评分应显式扣除「窗口覆盖度」而不是继续调权重。
  4. 新增 skill_capacity 扫描段（规则 M/R）：以全路径为键，并标注该路径是否在本 profile 写权限内。
